# V1.1 前端端到端主流程打通实施方案

> 状态：实施方案草案
> 更新时间：2026-06-30
> 对应路线图：`FUTURE_WORK_PLAN.md` 的“V1.1 出版目标：前端可用全流程”

## 目标

把当前“底层能力基本具备，但前端链路不顺”的状态，推进到研究者可以主要通过前端完成：

```text
发现/投递文献
-> 入库
-> 触发解析
-> 触发元数据抽取
-> 触发分类抽取
-> 进入 MetadataReview / ClassificationReview
-> 审核通过并回填
```

这版 V1.1 的出版标准不是“所有增强项都完成”，而是“用户不离开前端也能走通一篇新文献的主流程，并且每一步知道下一步该做什么”。

## 非目标

- 不做完整后台任务队列系统。第一版可以使用同步/短任务触发，加清晰 loading、结果和失败提示。
- 不做大规模自动采集调度。采集仍以人工闸门、小批量验证为主。
- 不做完整前端上传创建 work。`_inbox` + `/inbox` 已满足 V1.1 的手动投递路径。
- 不做 BibTeX/RIS、综述矩阵、Dashboard 深度增强。它们保留在后续队列。
- 不把元数据模板和分类规范一次性完善到最终形态；本阶段只为抽取入口与审核闭环提供最小模板版本化基础。

## 当前断点

### 已有能力

- `/inbox` 可 dry-run 预览并执行手动摄入。
- `/topics` 可查看主题、触发 collect、触发 resolve。
- `/intake` 可审核候选并 promote。
- WorkDetail 可触发 parse。
- MetadataReview 可审核已有 `metadata_extractions`。
- ClassificationReview 可审核已有 `classification_extractions`。
- 后端已有 `scripts/literature_metadata_extract.py` 和 `scripts/literature_classification_extract.py`。

### 主要缺口

- 主题创建、种子/关键词/显式 ID 输入仍偏 CLI，不够前端化。
- collect/resolve/promote 成功后缺少自然的下一步引导。
- parse 成功后没有前端按钮触发 metadata/classification extraction。
- metadata/classification extraction 没有 API 薄适配器。
- 多步骤任务反馈不统一，用户不知道“为什么列表为空”和“下一步做什么”。
- 缺少真正从前端走完一篇新文献的端到端 smoke。

## 架构原则

1. **薄 API，不复制脚本业务逻辑**  
   新 API 只解析请求、调用已有 nucleus/脚本函数、整形返回。需要抽公共函数时，应把逻辑从 CLI 提到 core，而不是在 API 里重写。

2. **小批量、安全触发**  
   元数据抽取和分类抽取第一版只支持单 work 或小批量，不做全库重跑按钮。

3. **每一步可解释**  
   前端必须显示状态、结果、失败原因和下一步入口。

4. **不破坏现有审核门禁**  
   抽取结果仍进入 review 队列，不绕过 MetadataReview / ClassificationReview。

5. **健康检查仍是最终守门**  
   端到端 smoke 后必须跑 `scripts/healthcheck_library.py --json`。

## Agent 分工建议

最多 4 个子 agent 并行：

1. **Agent A：抽取 API 与脚本 nucleus**
   - 负责 metadata/classification extraction 的后端触发入口。
   - 所属文件：`api/routes/*`、`scripts/literature_metadata_extract.py`、`scripts/literature_classification_extract.py`、相关 tests。

2. **Agent B：前端主流程与 WorkDetail 引导**
   - 负责 WorkDetail、api.js、跳转、状态提示、抽取按钮。
   - 所属文件：`web/src/api.js`、`web/src/views/WorkDetail.vue`、必要组件。

3. **Agent C：采集/主题/候选前端可用性**
   - 负责 TopicsReview / IntakeReview 的“无 CLI 可操作入口”和 promote 后下一步。
   - 所属文件：`web/src/views/TopicsReview.vue`、`web/src/views/IntakeReview.vue`、`api/routes/intake.py` 如需薄补。

4. **Agent D：端到端 smoke、文档与复核**
   - 负责 smoke 脚本/手册、测试矩阵、文档更新和两轮复核。
   - 所属文件：`tests/`、`docs/superpowers/reviews/`、`README.md` 或 runbook。

要求：

- 每个 agent 只改自己的责任范围，不回滚别人改动。
- 每个 agent 输出改动文件、测试命令、剩余风险。
- 主线程至少做两轮复核：第一轮功能路径，第二轮文档/测试/健康检查。

## 实施阶段

### Phase 0：基线复核

目标：确认当前状态，防止在错误假设上开发。

- [ ] 运行 `git status --short --branch`，记录未提交文件。
- [ ] 运行 `scripts/healthcheck_library.py --json`。
- [ ] 运行 `pytest tests\ -q`。
- [ ] 运行 `npm.cmd run build`。
- [ ] 手动或 Playwright 打开 `/inbox`、`/topics`、`/intake`、`/works/:id`、`/metadata`、`/classification`，记录当前断点。

验收：

- 基线命令通过，或明确记录既有失败。
- 形成一份短基线记录，放入后续 review/result 文档。

### Phase 1：抽取 API 薄适配器

目标：让前端能触发单 work / 小批量 metadata 与 classification extraction。

建议新增端点：

```text
POST /api/metadata/extract
POST /api/classification/extract
```

请求示例：

```json
{
  "work_ids": ["W-..."],
  "force": false,
  "limit": 5
}
```

返回示例：

```json
{
  "ok": true,
  "created": 1,
  "skipped": 0,
  "failed": [],
  "next": {
    "metadata_review": "/metadata?status=pending&search=W-..."
  }
}
```

实施要点：

- 优先从 CLI 脚本中抽出可调用函数，例如 `run_metadata_extraction_for_work_ids(...)`、`run_classification_extraction_for_work_ids(...)`。
- API 不直接拼 prompt、不直接写复杂业务逻辑。
- 第一版可以同步执行，但必须限制数量，避免误触全库重跑。
- 失败要返回 work_id、阶段、错误信息。
- 已有 pending/recent extraction 时默认 skip，除非 `force=true`。

测试：

- [ ] fixture DB 单 work 触发 metadata extraction，生成 `metadata_extractions` pending 行。
- [ ] fixture DB 单 work 触发 classification extraction，生成 `classification_extractions` pending 行。
- [ ] 无 `content_md_path` 时返回可读失败，不崩溃。
- [ ] 已有 pending/recent extraction 时默认 skip。
- [ ] `force=true` 行为有测试。

### Phase 2：WorkDetail 下一步工作台

目标：用户进入新 work 后，能看到“下一步该做什么”。

WorkDetail 增加一个紧凑流程条：

```text
源文件 -> 解析 -> 元数据抽取 -> 分类抽取 -> 审核
```

每一步显示：

- 当前状态：未开始 / pending / succeeded / failed / 有待审核结果 / 已审核。
- 可执行按钮：触发解析、触发元数据抽取、触发分类抽取、去审核。
- 失败原因和重试入口。

实施要点：

- parse 状态使用现有 `/api/parse/status`，必要时先按当前单源语义展示。
- metadata/classification 是否有待审核结果，可通过现有列表接口按 `search=work_id` 或新增轻量 summary。
- 抽取按钮调用 Phase 1 新 API。
- 成功后提供跳转到 MetadataReview / ClassificationReview 的链接。

测试：

- [ ] WorkDetail 构建通过。
- [ ] 对 parse succeeded 的 work 显示抽取按钮。
- [ ] 抽取成功后显示“去审核”。
- [ ] API 失败时显示可读错误。

### Phase 3：采集与摄入前端收口

目标：减少“无候选时回 CLI”的断点。

TopicsReview：

- [ ] 支持创建主题，至少包含名称、描述、关键词/显式 arXiv ID/种子 ID。
- [ ] 支持编辑主题的 query_def 或简化表单。
- [ ] collect/resolve 后展示新增候选数量、重复数量、失败数量。
- [ ] 候选为空时给出“新建主题/添加种子/触发采集”的前端路径。

IntakeReview：

- [ ] promote 成功后展示新 work 链接。
- [ ] 对 failed 候选展示原因和下一步建议。
- [ ] 对 `needs_better_copy` 明确提示 V1.1 是否支持替换；若仍不支持，给出手动处理路径。

InboxReview：

- [ ] 摄入成功后展示新 work 链接列表。
- [ ] 提供“打开第一个新 work”按钮。

测试：

- [ ] topic create/edit API 或前端调用有测试。
- [ ] promote 返回 work_id 后前端能跳转。
- [ ] 空状态不再只提示 CLI。

### Phase 4：统一任务反馈

目标：用户能理解每一步发生了什么。

统一显示字段：

- 操作名。
- 输入对象数量。
- 成功数量。
- 跳过数量。
- 失败列表。
- 下一步链接。

适用操作：

- collect
- resolve
- promote
- ingest execute
- parse trigger
- metadata extract
- classification extract

第一版不要求统一任务表，但前端交互应尽量统一。

测试：

- [ ] 关键操作失败时不会只弹 raw JSON。
- [ ] 成功后有下一步入口。

### Phase 5：端到端 smoke

目标：证明 V1.1 出版目标已达成。

推荐 smoke 路线 A：手动 inbox

```text
/inbox 放入小 PDF
-> 前端 plan/execute
-> 打开新 WorkDetail
-> 触发 parse
-> 触发 metadata extract
-> 触发 classification extract
-> MetadataReview 批准
-> ClassificationReview 批准
-> healthcheck 零问题
```

推荐 smoke 路线 B：collector

```text
/topics 新建主题/种子
-> collect
-> resolve
-> /intake 审核并 promote
-> 打开新 WorkDetail
-> parse/extract/review
```

验收命令：

```powershell
.\.venv\Scripts\python.exe -m pytest tests\ -q
.\.venv\Scripts\python.exe scripts\healthcheck_library.py --json
npm.cmd run build
```

必须额外保存：

- smoke 输入对象。
- 每一步截图或日志摘要。
- 新 work_id。
- 新 metadata/classification extraction id。
- 最终 healthcheck 输出。

## 两轮复核

### 第一轮：功能复核

- 新 API 是否薄适配，是否复用脚本/core 逻辑。
- 单 work / 小批量是否可控，是否避免全库误触发。
- 前端是否能从新 work 走到审核页面。
- 失败是否可读，下一步是否明确。

### 第二轮：治理复核

- `FUTURE_WORK_PLAN.md` 是否仍只保留路线图，不塞完成流水账。
- 完成项是否写入 review/result 或 `docs/PROJECT_HISTORY.md`。
- `README.md` / `TECHNICAL_OVERVIEW.md` 是否需要更新操作入口。
- 是否新增了过时 CLI 提示或历史路径误导。
- 文档漂移 grep 是否可解释。

## 发布判定

可标记为“V1.1 前端可用版”需同时满足：

- 前端 smoke A 或 B 至少一条完整通过。
- WorkDetail 能引导 parse -> metadata extract -> classification extract -> review。
- MetadataReview 与 ClassificationReview 能承接新抽取结果。
- healthcheck 零问题。
- `pytest tests\ -q` 与 `npm.cmd run build` 通过。
- 完成结果落盘到 `docs/superpowers/reviews/2026-xx-xx-v1.1-frontend-end-to-end-flow-result.md`。

## 风险与取舍

- 同步执行抽取可能较慢，但第一版可接受；若超时或阻塞明显，再拆后台任务。
- 抽取 API 直接调用 CLI 脚本内部函数时，要避免打印、退出进程或读取真实环境导致测试不稳定。
- 前端 collect 若触网失败，必须能解释失败原因，而不是让用户误以为没有相关文献。
- 不要为了“全前端”绕过审核门禁；自动抽取结果仍必须进 review。
