## 2. 目标与发布顺序

用户应能从客户端完成：查重并补录 → 按实际批次/用途核对范围 → 预览缺口与预算 → 有限补解析并恢复中断 → 查看固定版本材料 → 整理与核查 A/R → 按条件导出。服务器负责备份、恢复、一致性和明确的执行状态。

| 阶段 | 交付 | 工单与依赖 | 放行条件 |
|---|---|---|---|
| A 数据与接入保障 | 当前数据保全、备份入口、补录回执、错误诊断 | U00、U01、U02、U03 | 客户端补录可对账；备份可恢复；错误能判断是否已提交 |
| B 有限补解析 | 固定选集、持久任务、预算和恢复 | U04 与 U05 必要子集；并发 1 即可交付 | 重放不重复消耗；旧 epoch 不能登记；维护能排空 |
| C 材料与书目 | VLM/融合阅读验收、版本与发表归属、可选列导出 | U06、U07、U08；U08 基础字段可先交付 | 页面/API/CLI 固定同一材料；字段不混版本；导出可追溯 |
| D 科研工作流 | Work 级 A/R、谱系/依赖/引用管理与旧问题复验 | U09、U10 | 独立核查可追溯；历史数据问题逐项验收 |
| 各阶段收尾 | 客户端能力、文档、迁移及发布回执 | U11 贯穿各阶段 | 候选、上线、内容验收分别有证据 |

上表是实现依赖顺序，不是规划必须等待的顺序：**C/D 阶段的科研规划现在开展，A/B 阶段只补必要基础闭环。** 允许多个可独立审查的提交；按验收门槛分批发布。客户端持续补录期间做候选开发和隔离测试；生产停写只发生在安排好的快照/迁移/切换窗口。VLM 暂保守并发 1，实际预算和优先清单在执行前填写；不以线程数代替额度控制。

基础收口标准：能查重补录并对账，能获得可恢复备份和回执，能按精确清单在预算内解析并安全恢复，能查明失败阶段，能读取固定材料。跨请求提速、多主机 worker、复杂调度、公用报表平台、XLSX、高级图分析及代码/数据发布协议重构均不作为这一轮必交项。U05 的安全恢复部分必须完成，性能部分保留后续设计。

## 3. 统一数据与执行约定

### 3.1 代码发布与数据快照

短期保留现有统一 manifest/authority 协议，明确区分代码版本、数据快照版本及部署时绑定关系。每次发布从认证当前写者准备输入，停写后重做最终快照、验证目标再交接 epoch。不得 restore 旧数据后裸拷贝 `.sqlite` 修补，不得只比较 works 数量。

后续可将不可变代码包与数据快照分开生成，由部署描述符绑定两者，并记录兼容 schema/contract、源 epoch、快照时间、摘要及迁移记录；必须升级旧 restore/strict/authority 的共同契约后才启用，不能仅改目录布局。仍需两库一致性边界与固定资产闭包。普通备份不切换代码或 epoch。

slot 回收应先列出全表行差集、固定资产元组、未完成任务、WAL 数据及跨 slot 路径依赖，确认独立可恢复副本和保留期；默认生成可审查清单。Windows 上只针对已解析、验证范围内的绝对路径执行回收。释放目录锁不能成为删除独有数据的理由。

### 3.2 统一选择语义

摄入批次、研究批次、解析执行批次分别建模。现有 `request_id` 表示一次幂等摄入操作，可能一文件一个 ID，不天然等于用户说的“这批”；研究 batch_id 也不能代替摄入批次。

统一选择器至少支持显式 Work/Source、摄入 request_id 集合、后续摄入批次 ID、首次入库时间、Source 导入时间、用途文本及用途登记时间。时间区间采用 `[from,to)`，明确时区；无可靠历史字段时标为未知，不从文件 mtime/updated_at 猜测。用途文本和用途时间必须命中同一条 ingest_note。不同维度 AND，同维度任一/全部显式规定。

预览分别输出 Work、Source、Parse、已完成目标后端、缺融合、隔离、活动任务、未知状态计数及原因。多 Source 的 Work 必须指定适用 Source/策略；“有 PyMuPDF”不自动等于“需要 VLM”。本批补解析由用户目标、适用版本和既有 VLM/融合资产共同决定。

执行使用冻结的清单：Source ID、PDF SHA、目标后端/参数、基线 Parse、选择原因、优先级、估计页数、清单摘要。执行时重新检查活动任务和 Source 状态；变化条目暂停并报告，不静默扩大清单。无需等完整版本模型即可以明确 Source ID 开始。

### 3.3 作业、额度和恢复

扩展现有 producer/operation 表与查询入口，避免另造互不相认的任务体系。持久保存请求幂等键和参数摘要、Source、预留版本、所属 epoch、执行租约及代次、目标/实际后端、上游 task_id、阶段时间、产物和错误。

建议状态：queued → running/submitting → upstream_submitted → artifacts_ready → registered；另有 failed、blocked_budget、cancel_requested/cancelled、submission_unknown。状态名最终以迁移契约为准。先持久登记再调用外部服务；收到上游 ID 后立即持久化，不等整个解析返回。上游已接收而本地未拿到 ID 的窗口无法凭本地事务消除，必须保留“不确定”，优先按上游标识查询或人工核实，不自动新提交。

同幂等键同参数返回原 job；同键不同参数冲突。`force` 是创建新解析版本的明确意图，不是失败重试策略。已有产物仅恢复上传/登记；不能用重新跑解析冒充 resume。历史 Work 级“最近成功解析”摘要只表达可用成果，新任务进度必须按 job/Parse 精确查询，两者并列。

预算区分本轮篇数/页数/提交次数上限、本地预留、上游已用额度和未知消耗。额度单位以实际 provider 为准；本地计数不能声称等于账户余额。提交前跨进程原子预留，失败仅在确认未产生费用时释放；未知结果仍占预留。轮询不算新解析提交，重试上限与退避持久化。额度耗尽暂停剩余队列并生成剩余清单。

### U04｜按批次/用途预览及限额补解析 CLI

关联：#7、#10、#13、N01/N14；依赖 U02 选择语义、U03 诊断。批次实体未完成时可先用精确清单。

- 提供 `parse plan/run/status/resume` 专用入口（拟议命令），共享第 3 节选择器；plan 默认只读，输出 JSON/CSV 清单、分母、排除原因、预算估算、优先级及未决项。
- `run` 必须输入已冻结计划、明确后端和最大篇数/页数/提交次数；预算不足停止接收剩余项。先以执行并发 1 上线，但必须已有持久幂等与额度预留，不能只写客户端 for 循环。
- 清单按稳定顺序/用户优先级分块，记录每项回执；断线后从既有任务恢复。区分“额度暂停”“失败待定位”“已解析但缺融合”“已完成”。
- 验收：同计划重复执行不新建相同任务；额度不够时只执行允许子集；同 Work 多 Source 不误选；用途+时间跨记录反例不匹配；补录继续发生不扩大本计划。真实 VLM 未验收前只提供计划，不自动消费整批额度。

### U05｜持久作业、有界并发和 authority 边界

关联：#7。依赖 U03/U04 的幂等与预算契约；详细方案见[并发设计](bounded-concurrency.md)。

- 任务接收与最终提交使用短 authority 临界区；长解析/网络阶段持有 Source/job 所有权和资源 pin，释放全局写锁。最终登记复核当前 epoch、租约代次、Source 版本、SHA 和任务状态；检查与提交在同一受保护边界。
- 队列先于提速交付：跨请求/进程限制 provider 任务、上传/下载、内存/缓存空间；单请求 ThreadPoolExecutor 不能充当全局限流。SQLite 短事务原子预留版本；同 Source 约束覆盖 trigger/resume/release，而非仅 parse_source。
- 维护停止接收新任务，排空或持久暂停，等待所有提交完成再快照；旧进程迟到结果不能登记。取消先停止后续步骤，已提交云任务须跟踪结果和费用，不能声称必然退款。
- 验收：不同 Source 可测量重叠；同 Source 仅一条版本分配；响应丢失不重跑；上游成功/本地崩溃恢复；多 worker 总并发不超限；冻结/交接拒绝旧提交；清理不删除 pin/staging。未测容量前不承诺 2/4/8 并发。

### U06｜VLM、融合与网页固定材料验收

关联：#10；依赖 U03，真实样本依赖明确预算。

- 优先复用已有样本，分别核查原 PDF、content.md/json、content.merged.md、detail.json 的固定身份、SHA/bytes、登记及取回。Parse 成功、融合成功、A 核查和网页阅读分别报告。
- 浏览器按正式 CA 信任访问，502 与证书问题分别定位；不通过关闭 TLS 验证交付。页面明确选中的 Parse/Source/论文版本，缺融合时有说明，不将旧合并版当作新解析。
- 验收：公式/表格/图片样本对照 PDF；显式 VLM、auto 降级、融合旁路失败分别覆盖或标未执行；真实 VLM 至少一个点名样本经允许预算成功后才宣布服务恢复。内容质量核查独立于工程测试。

### U07｜论文版本与发表归属契约

关联：#6、#11、WF-002/008/012。先出可审查 schema/迁移样例，再实现。

- 区分 Work、论文语义版本、PDF 字节版本、Parse 版本和 A 修订；Source 是具体文件，不能单凭内容 SHA 或解析时间确定论文版本。首选版本按用途显式选取，现有研究引用仍固定原版本。
- 复用已有 A 字段和 publication_status，定义 publication_container（期刊/会议论文集/系列）、publisher/机构及角色、hosting_platform；日期事件保留精度、来源、核查状态和适用论文版本。
- 旧 venue 原值及历史保留，能证实再映射；含糊值待核，不凭 arXiv 域名推断会议录用。目录投影、CLI/API、页面、BibTeX/RIS/CSV 使用共同字段语义。
- 验收：仅预印本、未确认录用、后续正式发表、机构报告、无容器及旧冲突值；不混拼成不存在的“最新书目”，不继承旧审核/采纳，不触发全库 A 重做。

### U08｜按条件筛选与自选列导出

关联：#12、N14、PLATFORM-006；复用 U04 选择器，版本字段依赖 U07，基础列可先交付。

- 服务端字段白名单供网页/CLI 共用：稳定键、含义、类型、来源、支持的操作、必带/不可选原因。首版 CSV，自选/排序列；保留 BibTeX/RIS/旧矩阵，XLSX 后置。
- 默认一 Work 一行，必带 work_id；正式书目与待核工作清单显式分开，待核状态不可取消。多作者/用途/资源列表或关联表表达，禁止 JOIN 造成重复 Work。
- 预览冻结选集及 A/投影修订，下载用同一快照；过期则拒绝并要求重新预览或明确提供旧快照。附查询、列顺序、时间/时区、行粒度、固定版本、匹配/排除数和未决项。
- 首版时间支持可靠的入库/Source 导入/用途登记字段；发表事件与 A 修订时间只在相应契约可靠时开放。无值、未知、不适用和不支持分开。
- 验收：跨页全部结果、显式选择、空结果、超限、中文/换行/逗号、公式样式文本保护、标识符保持文本；未知列拒绝，查询变化不静默截断；导出不触发解析、生产、审核或采纳。

### U09｜Work 级 A/R 整理与独立核查

### 8.2 数据对象与边界

| 对象 | 负责表达 | 不能代替 |
|---|---|---|
| Work | 研究对象的聚合身份 | 某一个 PDF 或已核实发表版本 |
| 论文版本 | 预印本修订、录用/正式版本等明确版本及关系 | 文件 SHA、最新解析时间 |
| Source / Parse / 固定材料 | 实际文件及某次解析与可回读资产 | A 已核查、内容结论可靠 |
| A 修订与字段证据 | 适用论文版本的书目、资源、缺失/冲突及核查依据 | 人已阅读/采纳、全部资源实际可用 |
| R 条目及版本 | 引用方材料中的书目条目、定位、身份候选和核查状态 | 已证实引用边或已入库的被引全文 |
| 引用边 | 谁在何固定材料中引用谁、证据及核验状态 | 仅靠标题相似得到的关系或科学支持关系 |
| C/D 记录与依赖 | 现行契约内研究成果、范围、固定版本和审核轨迹 | 全文普遍结论、跨篇自动综合 |
| 反馈、复审与采纳 | 针对具体记录版本和范围的事件 | 一个覆盖所有层的“完成”状态 |

版本模型先定义语义和关联约束，再决定是否新增表；不得仅为这些概念重命名或复制现有字段。元数据投影要保存实际选用修订及来源，legacy/人工修订不可冒称独立核查 A。版本变更先做字段影响和真实依赖分析，再提示需复核范围，历史固定成果继续可读。

### 8.3 A/R 任务状态与执行契约

一份工单包括：目标 Work/适用 Source/Parse/材料、任务层 A 或 R、具体补缺范围、既有成果/反馈、复用决定、基线修订、证据要求、执行上下文、幂等标识和预期回执。为 A/R 分别定义冲突域，避免因同 Work 就阻塞所有互不冲突的工作。

任务状态（待领取/执行/待复核/失败/完成）与记录状态（候选/稳定/历史/有争议等现有契约）分列；人的采纳也分列。独立审核绑定实际被审修订和来源材料，并记录真实独立上下文证据；结构校验只负责必填、类型和依赖，不承担科学判断。

执行顺序：前置盘点 → 明确复用或补缺 → 生成工单 → 外部 Agent 提交候选 → 服务端结构/依赖校验 → 独立上下文回看材料 → 追加审核事件 → 更新适用投影/显示 → 人按范围判断。已有 stable 的追加复审仍必须留事件，不能因状态相同而丢弃。

提交时校验基线修订；其他 Agent 已更改时返回冲突及最新引用，不覆盖。失败任务保留已提交部分及待办项，不整批从头生产。新反馈可形成修订任务，但不会自动把人的既有采纳扩大到新版本。

### 8.4 引用与研究谱系

首版先做可审查的引用列表、身份匹配和出处详情，再提供同一数据源的轻量图视图。图中节点/边必须能返回 Work、具体材料、R 条目、核验状态与证据；未匹配条目可作为待核对象，不伪造 Work。按候选/已核/历史/退役及版本范围筛选，明确计数单位。

身份匹配不要求被引文献先有全文或进入主题批次，但必须满足正式 identity_basis。引用事实核验固定引用方材料；被引文献身份匹配成功，不表示已经核查其内容，也不表示引用支持当前科学主张。

纠错、归并和退役通过现有正式 API，保留历史映射与原因；不得物理删除被依赖记录。退役后有效候选列表和统计排除该项，历史导出/旧边仍可解释其当时来源。重复和“占位测试条目”分别处理。

Work 谱系显示版本、A/R/C/D、审核/反馈/采纳及任务关联；多个研究 scope 并列，不以时间戳决定唯一科研头。依赖缺失、历史合法版本和推荐新基线用不同提示。高级中心性、社区发现、自动知识图谱推理后置。

### 8.5 检索、导出与科研复用

第一步完成 #12 的 Work 元数据表：按时间/用途/批次选择，选列，说明适用版本及状态。第二步承接 N14 的研究材料检索：在既有受控概念、研究方面/作用、位置和 scope 中组合条件，按真实关联查询；不能把多个条件分别命中不同研究单元当作同一单元命中。

Work 表与研究记录/单元表分开选择行粒度；导出固定 Work/Source/Parse/记录修订、查询、范围、定义版本、证据位置及排除项。Markdown/JSON/关联 CSV 承载科研材料，BibTeX/RIS 保持书目语义。历史导出不随上游更新静默改变。

导出和跨批复用均提示开放反馈、依赖差异和核查范围；用户可明确选择历史版本，但系统不能把历史/争议内容标成当前稳定可用。N14 的当前检索与材料导出不要求先完成 N10 的跨篇科学综合。

| S4 研究材料检索 | N14 研究单元条件、关联导出和图视图完善 | 多条件只匹配同一关联范围；候选与已核边区分；不同 scope 不静默合并 |

这些是科研功能设计与工程验收阶段，不承诺自动完成所有文献的 A/R/C/D 内容生产。真实内容样例先复用已有适合材料；新增外查/解析按明确范围和预算执行。旧 CONTENT/ONTOLOGY 问题继续独立核验，P1—P6 和正式 ontology v1 保持原边界。

### 8.7 实现前须提交的具体设计附件

每个科研批次在编码前补齐：现有 API/字段盘点及复用表；新增/调整契约和三类样例（正常、缺失、冲突）；页面状态与操作流；迁移及旧客户端兼容；验收 fixture 和真实样例选择。U07 优先提交“预印本→正式版、旧 venue 含糊”的迁移样例，U09 优先提交“一篇 Work 已有 A、R 部分完成且有开放反馈”的完整工单/回执样例。
