# V1.1 受约束广泛发现与检索方案实施计划

> 状态：实施方案草案
> 更新时间：2026-06-30
> 对应路线图：`FUTURE_WORK_PLAN.md` 的“受约束广泛发现与检索方案 V1.1”

## 目标

补齐 collector 现有“只适合显式 arXiv ID / 种子文献 / GitHub 论文 PDF”的发现短板，让用户可以从前端或 CLI 提供更自然的检索意图，并把检索结果以可解释、可审核的方式送入候选池。

第一版必须同时支持两类入口：

1. **主题检索**：用户填写主题名、描述、axis_hint、关键词、种子材料，系统起草或执行检索方案。
2. **固定字段检索**：用户已知明确名称或标题时，可以直接按名称/标题找目标材料。例如：
   - “GPT-5.6 system card”
   - “Claude 4 system card”
   - “某篇文献的完整标题”
   - “某机构技术报告标题”

这版的出版标准不是“全自动抓全网”，而是“用户能把一个主题或一个已知名称交给系统，得到一批带来源、理由、证据和去重线索的候选，并经 intake 审核后再入库”。

## 非目标

- 不做无约束大规模爬取。
- 不把搜索结果直接写入 `works`。
- 不跳过 intake 审核、轻闸门、重闸门和人工 promote。
- 不在 collector 中扩展分类词表或 ontology vocab。
- 不要求第一版实现所有来源适配器；先实现最小可验证来源组合。
- 不要求第一版做持续调度、订阅、自动循环更新。
- 不把 GitHub repo / Hugging Face model 本身一律视为 `work`；只有可归档的文档对象或明确文献材料才进入候选。

## 用户场景

### 场景 A：按主题发现

用户在 `/topics` 新建主题：

```text
主题名：frontier model system cards
描述：收集主要前沿模型的 system card / model card / safety report
轴归属：artifact_focus=system_card / model_card
关键词：system card, model card, safety report
```

系统先生成检索方案，包含 query、来源、域名线索、排除词、候选上限和判断准则。用户确认后执行检索，结果进入候选池。

### 场景 B：按明确名称检索

用户知道目标名称：

```text
名称：GPT-5.6 system card
材料类型：system_model_card
期望来源：官方发布页优先，其次可信镜像或引用页
```

系统围绕名称做精确检索，不要求用户提供 arXiv ID、DOI 或种子文献。

### 场景 C：按文献标题找全文

用户知道论文标题但不知道 DOI/arXiv：

```text
标题：A Survey of AI Evaluation Methods for Frontier Models
材料类型：research_article / survey_review
```

系统优先查结构化学术来源，再用通用 Web 搜索补足 PDF、HTML、机构页和作者页。

## 设计原则

1. **先起草方案，再执行检索**
   - 搜索前先产生 `search_plan`，用户或 agent 可审查 query、来源和边界。
   - 直接执行只允许用于固定字段精确检索和显式 URL。

2. **主题名不是无限制搜索词**
   - 主题名可作为检索上下文，但必须被展开为有来源、有上限、有排除词的 query。
   - 主题检索默认小批量，先看候选质量。

3. **固定字段检索是一等入口**
   - `name` / `title` / `known_url` / `doi` / `arxiv_id` / `github_url` 是独立输入，不应被迫包装成主题。
   - 名称检索优先解决“我知道我要找什么，但不知道在哪”的需求。

4. **结果只进候选，不进 works**
   - 所有发现结果先进入 `discovery_hits` 或 `intake_candidates` 的扩展字段。
   - promote 仍必须经人工审核和现有 ingest bridge。

5. **每条结果必须可解释**
   - 保留 query、来源、URL、标题、snippet、命中理由、来源类型、可信度、去重 key。

6. **来源可信度分层**
   - 官方/机构域名优先，但不能只靠固定 allowlist。
   - 通用 Web 搜索用于发现未知入口，再由来源判断和人工审核收口。

7. **agent 与后端都可执行**
   - 后端 Python/CLI 可以执行结构化来源和固定字段搜索。
   - agent 可调用 web-access 等网页检索能力，把结果结构化写回系统。

## 核心边界与设计哲学

Discovery 不负责判断真理，只负责产生可审计线索；Intake 负责候选审查；Ingest 才负责入库。

因此 V1.1 的最小闭环必须保持三层隔离：

1. **discovery run**：记录用户输入、检索方案、执行者、状态和错误。
2. **discovery hit**：记录一次检索命中及其证据，不代表系统已经认可该材料。
3. **intake candidate**：只有人工接受 hit 后才创建或复用，仍需现有 intake 审核与 promote。

### 与现有 `/intake/collect` 的边界

现有 `/api/intake/collect` 和 `collector.collect.collect_once` 仍是“已知 ID / 种子 / GitHub URL 的采集入口”，主要读取 `collection_topics.query_def.explicit_ids`、`seed_paper_ids` 和显式 `github_urls`，并直接创建 `intake_candidates`。

新的 `/api/discovery/*` 是“检索计划与命中证据池”，用于处理名称、标题、显式 URL 和主题扩展检索。两者不得互相隐式触发：

- `/intake/collect` 不负责开放 Web 检索或 discovery hit 记录。
- `/discovery/run` 不直接 promote、不下载 PDF、不写 `works`。
- 从 discovery 到 intake 的唯一正式桥梁是 `accept_hit_to_intake(...)`。

### V1.1 固定字段范围

设计上长期支持 `name` / `title` / `known_url` / `doi` / `arxiv_id` / `github_url` 等独立入口，但 V1.1 的实现范围需先收口。

已确认的 V1.1 范围：

- V1.1 必做：`name` / `title` / `known_url` / `topic plan`。
- V1.1 可复用旧链路：`arxiv_id` / `github_url`，通过现有 `/intake/collect` 或 CLI collect 进入 intake，不强行接入 discovery hit。
- V1.1 不做：`doi` discovery、`arxiv_id` discovery、`github_url` discovery。
- V1.2 可选增强：`doi` title/metadata 反查。

实现要求：

- API / CLI / 前端遇到 `doi` / `arxiv_id` / `github_url` discovery 输入时，必须给出清晰 unsupported 或“请走现有 collect”的提示，不能静默忽略。
- 本次实现不得为了“顺手统一入口”把 `doi` / `arxiv_id` / `github_url` 强行纳入 discovery hit。
- 如果未来决定把 `doi` / `arxiv_id` / `github_url` 也纳入 discovery，必须新开 V1.2 方案，并同步补齐 API、CLI、前端和测试。

## 数据模型草案

### 扩展 `collection_topics.query_def`

保持向后兼容，新增可选字段：

```json
{
  "explicit_ids": [],
  "seed_paper_ids": [],
  "keywords": ["system card", "model card"],
  "known_names": ["GPT-5.6 system card"],
  "known_titles": [],
  "known_urls": [],
  "search_profiles": [
    {
      "type": "system_card",
      "sources": ["web", "official_domain", "github", "huggingface"],
      "queries": ["GPT-5.6 system card", "\"GPT-5.6\" \"system card\""],
      "domains": ["openai.com"],
      "exclude_terms": ["reddit", "news", "forum"],
      "max_results": 20
    }
  ]
}
```

### 新增 `discovery_runs`

用于记录一次检索执行。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | `DR-{hex}` |
| `collection_topic_id` | 可空；主题检索时填写 |
| `mode` | `topic` / `name` / `title` / `url` / `doi` / `arxiv` |
| `input_json` | 用户输入快照 |
| `search_plan_json` | 执行前方案 |
| `executor` | `python` / `agent:web-access` / `manual` |
| `status` | `planned` / `running` / `succeeded` / `failed` |
| `created_at` / `updated_at` | 时间 |
| `error` | 失败原因 |

### 新增 `discovery_hits`

用于记录检索命中，避免过早污染 `intake_candidates`。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | `DH-{hex}` |
| `run_id` | 对应 discovery run |
| `collection_topic_id` | 可空 |
| `query` | 命中的 query |
| `source_type` | `web` / `official_domain` / `github` / `huggingface` / `openalex` / `crossref` / `semantic_scholar` / `manual_url` |
| `url` | 原始 URL |
| `canonical_url` | 规范化 URL |
| `title` | 检索标题 |
| `snippet` | 摘要片段 |
| `artifact_type_hint` | `system_card` / `model_card` / `technical_report` / `research_article` / `unknown` |
| `confidence` | `high` / `medium` / `low` |
| `reason` | 为什么认为值得进入候选 |
| `raw_json` | 原始返回 |
| `dedup_key` | URL/title/DOI/arXiv 等组合 key |
| `candidate_id` | 被提升到 `intake_candidates` 后回填 |
| `review_status` | `pending` / `accepted` / `rejected` |
| `review_note` | 人工拒绝或修正说明 |
| `primary_source` | `true` / `false` / `unknown` |
| `content_type` | `html` / `pdf` / `metadata` / `repo` / `model_card` / `unknown` |
| `verification_status` | `unverified` / `url_verified` / `content_checked` / `failed` |
| `observed_at` | 命中被记录的时间 |

去重范围：

- `discovery_hits`：同一 `run_id + dedup_key` 内去重，避免一次 run 内重复命中刷屏；不同 run 可以保留各自命中，便于审计检索方案质量。
- `intake_candidates`：接受 hit 时按全局 `arxiv_id` / `doi` / `url_canonical` 复用已有候选，不能为同一 canonical URL 重复创建候选。
- title-only hit 不作为全局强去重依据，只能作为 low-confidence 线索。

### `intake_candidates` 最小扩展

第一版可不立刻大改 `intake_candidates`，只在从 `discovery_hits` 提升时复用现有字段：

- `source_type`
- `source_url`
- `title`
- `doi`
- `arxiv_id`
- `url_canonical`
- `raw_meta`
- `collection_topic_id`

`raw_meta` 至少写入：

```json
{
  "discovery_hit_id": "DH-...",
  "discovery_run_id": "DR-...",
  "query": "...",
  "source_type": "web",
  "artifact_type_hint": "system_card",
  "primary_source": true,
  "content_type": "pdf",
  "verification_status": "url_verified",
  "reason": "...",
  "snippet": "..."
}
```

### discovery accept 轻闸门适配

从 `discovery_hits` 接受为 `intake_candidates` 时，不能假设所有材料都是论文。V1.1 应按材料类型采用最小可解释闸门：

- 有 DOI/arXiv：复用现有强标识去重和轻量闸门。
- 有 URL：优先用 `canonical_url` / `dedup_key` 做候选去重；允许无 DOI/arXiv 的 HTML、PDF、官方报告页、system card、model card 进入 intake。
- 只有 title、无 URL：允许保留为 low-confidence candidate 或只保留在 discovery hit，默认不批量接受。
- `resolution` 不应被强行判为论文语义；第一版可写 `pending` 或 `new`，并在 `raw_meta` 保留 discovery 证据，后续由 intake 审核决定。
- accept 不下载 PDF、不 promote、不绕过 review_status。

## API 草案

### 起草检索方案

```text
POST /api/discovery/plan
```

请求：

```json
{
  "mode": "topic",
  "topic_id": "CT-...",
  "name": "",
  "title": "",
  "known_url": "",
  "artifact_type_hint": "system_card",
  "constraints": {
    "max_results": 20,
    "prefer_official": true,
    "allow_general_web": true
  }
}
```

返回：

```json
{
  "plan": {
    "mode": "topic",
    "queries": [
      "\"GPT-5.6\" \"system card\"",
      "\"GPT-5.6\" \"model card\""
    ],
    "sources": ["web", "official_domain", "github", "huggingface"],
    "domains": ["openai.com"],
    "exclude_terms": ["reddit", "forum"],
    "max_results": 20,
    "acceptance_criteria": [
      "official or primary source preferred",
      "document-like artifact required",
      "must preserve source URL and reason"
    ]
  }
}
```

### 执行检索

```text
POST /api/discovery/run
```

请求：

```json
{
  "topic_id": "CT-...",
  "mode": "name",
  "input": {
    "name": "GPT-5.6 system card",
    "artifact_type_hint": "system_card"
  },
  "plan": {
    "queries": ["\"GPT-5.6\" \"system card\""],
    "sources": ["web", "official_domain"],
    "max_results": 10
  },
  "executor": "agent:web-access"
}
```

返回：

```json
{
  "run_id": "DR-...",
  "status": "planned",
  "hits_created": 0,
  "hits": []
}
```

语义约束：

- `POST /api/discovery/run` 负责创建 run，并保存 `input_json` 与 `search_plan_json`。
- 当 `executor="agent:web-access"` 时，API 不直接执行 Web 搜索；run 状态应为 `planned` 或 `running`，等待 agent 通过回填端点写入 hits。
- 当 `executor="manual"` 且 mode=`url` 时，可以同步创建一条 `manual_url` hit。
- 当 `executor="python"` 时，V1.1 只允许结构化来源或 mock/test source；真实通用 Web 搜索留给 agent/web-access 或后续 API key 方案。

### 查看检索命中

```text
GET /api/discovery/runs
GET /api/discovery/runs/{run_id}
GET /api/discovery/hits?run_id=DR-...
```

### 将命中送入 intake

```text
POST /api/discovery/hits/{hit_id}/accept
POST /api/discovery/hits/batch-accept
```

效果：

- 根据 hit 创建或复用 `intake_candidates`。
- 运行 discovery accept 轻闸门适配，写入 `resolution` 或保留 `pending`。
- 不下载 PDF，不 promote。

## CLI 草案

脚本可先放入 `scripts/literature_discovery.py`，后续稳定后再考虑并入 `scripts/literature_intake.py`。

```powershell
# 按主题生成方案
uv run python scripts/literature_discovery.py plan --topic CT-xxxx

# 按明确名称生成方案
uv run python scripts/literature_discovery.py plan --name "GPT-5.6 system card" --type system_card

# 按标题生成方案
uv run python scripts/literature_discovery.py plan --title "Exact Paper Title" --type research_article

# 执行已保存方案
uv run python scripts/literature_discovery.py run --plan DR-plan.json

# 查看命中
uv run python scripts/literature_discovery.py hits --run DR-xxxx

# 接受命中进入 intake
uv run python scripts/literature_discovery.py accept --hits DH-1,DH-2
```

## 检索来源优先级

### 第一版必须支持

1. **通用 Web 搜索**
   - 用于发现未知官网、PDF、HTML、模型卡、系统卡、技术报告。
   - 可由 agent 通过 web-access 执行，第一版不要求后端直接接搜索引擎 API。

2. **官方/机构域名搜索**
   - 从 query 或用户输入中提取 domain hint。
   - 对系统卡、模型卡和技术报告优先。

3. **显式 URL**
   - 用户给 URL 时直接创建 discovery hit。
   - 后续由轻闸门/人工审核判断是否进 intake。

4. **结构化学术标题搜索**
   - OpenAlex / Crossref / Semantic Scholar title search。
   - 适合“我知道文献标题但不知道 DOI/arXiv”的场景。

### 第一版可选

- GitHub README / releases / repo metadata。
- Hugging Face model card。
- DOI/arXiv 反查增强。

## Agent 执行协议

当使用 agent / web-access 执行检索时，必须输出结构化 JSON，不允许只给自然语言总结。

推荐任务指令：

```text
请执行 discovery search run。

输入：
- mode: name
- name: GPT-5.6 system card
- artifact_type_hint: system_card
- preferred_sources: official_domain, web
- max_results: 10

要求：
1. 使用通用 Web 搜索和官方来源优先策略。
2. 不要登录，不要绕过访问控制。
3. 每个结果输出 title/url/source_type/snippet/reason/confidence。
4. 标出是否看起来是 primary source。
5. 不要编造 URL；无法确认则 confidence=low。
6. 返回 JSON 数组。
```

返回格式：

```json
[
  {
    "title": "...",
    "url": "https://...",
    "source_type": "official_domain",
    "snippet": "...",
    "artifact_type_hint": "system_card",
    "confidence": "high",
    "reason": "Official model release page links to system card PDF",
    "query": "\"GPT-5.6\" \"system card\""
  }
]
```

## Agent 分工

建议至少 4 个子 agent，并行后交叉审核：

1. **Agent A：数据模型/API**
   - migration、core、API、后端测试。

2. **Agent B：CLI 与 agent 回填协议**
   - `scripts/literature_discovery.py`、agent JSON 回填入口、去重。

3. **Agent C：前端**
   - DiscoveryReview、TopicsReview 入口、固定字段表单、结果审核。

4. **Agent D：测试与文档**
   - smoke fixture、runbook、FUTURE/TECHNICAL/README 更新建议。

执行要求：

- 主 agent 必须明确给每个子 agent 分配互不重叠的文件/责任范围。
- 子 agent 不得只给自然语言总结；实现 agent 要提交补丁，审核 agent 要给文件/行号级发现。
- 第一轮实现后，至少安排一轮交叉审核；修复后再安排第二轮复核。
- 审核和汇总必须显式检查“幻觉 URL、偷懒省略测试、越界写 works、把主题检索变成无限抓取”四类风险。

## 两轮复核

### 第一轮：功能与边界

- 固定字段检索是否真的不依赖主题。
- 主题检索是否不会变成无限制关键词抓取。
- discovery hits 是否不会直接污染 `works`.
- accept hit 是否只进入 `intake_candidates`.
- agent 回填是否有去重和必填字段校验。

### 第二轮：搜索质量与治理

- 查询是否有过度发散风险。
- 官方/机构来源是否有清晰优先级，但不排斥通用 Web 搜索。
- 每条 hit 的 reason 是否足够支持人工审核。
- 文档是否明确“检索方案起草 -> 用户确认 -> 执行 -> 候选审核”。
- 是否保留失败、空结果、噪声过高的反馈路径。

## 发布判定

可标记为 V1.1 受约束广泛发现完成需满足：

- `discovery_runs` / `discovery_hits` migration 幂等。
- name/title/url/topic 四种入口至少后三种可用；topic 至少能生成 plan。
- V1.1 不支持的固定字段必须有明确 UI/API/CLI 提示，不能静默失败。
- agent/web-access 回填 hits 可进入系统。
- accept hit 只创建 intake candidate，不直接写 works。
- `/discovery` 页面可查看 run/hit 并 accept/reject。
- 两条 smoke 通过：一个 system/model card 名称检索，一个文献标题检索。
- 全量 pytest、healthcheck、npm build 通过。

## 决策结果

本轮方案修订确认采用以下默认选择；备选方案保留为后续扩展背景。

1. **固定字段范围**
   - 已选：方案 A。V1.1 只做 `name` / `title` / `url` / `topic plan`；`arxiv_id` / `github_url` 继续走现有 collect；`doi` 放到 V1.2。
   - 方案 B：V1.1 把 `doi` 也纳入 discovery，增加 DOI 元数据反查和测试。
   - 方案 C：V1.1 把 `arxiv_id` / `github_url` 也统一纳入 discovery hit，代价是需要重做旧 collect 与新 discovery 的边界。

2. **agent/web-access run 状态**
   - 已选：方案 A。`/run` 只创建 `planned` run，agent 回填后由系统改为 `succeeded` / `failed`。
   - 方案 B：`/run` 创建 `running` run，并由外部 agent 完成后回填和显式 finalize。

3. **title-only hit 的处理**
   - 已选：方案 A。没有 URL 的 title-only hit 只能留在 discovery，不能 batch accept。
   - 方案 B：允许人工逐条 accept，但必须写入 low-confidence 和 review note。

4. **非论文材料的 intake resolution**
   - 已选：方案 A。accept 后默认 `resolution='pending'`，由后续 intake/resolve 判断。
   - 方案 B：accept 后若 URL 去重无冲突则写 `resolution='new'`，更方便审核但可能显得过度认可。

5. **DiscoveryReview 首版布局**
   - 已选：方案 A。独立 `/discovery` 三栏页面，TopicsReview 只放入口和最近 run。
   - 方案 B：先嵌入 `/intake`，少一个页面但会让 intake 审核心智变复杂。

## 风险与取舍

- 通用 Web 搜索质量不稳定，第一版必须小批量、可解释、可拒绝。
- 官方域名优先不等于固定 allowlist；未知官方页仍需通用 Web 搜索发现。
- system card/model card 常以 HTML、PDF、博客或 release page 形式出现，不能只按 PDF 处理。
- GitHub/Hugging Face 项目页可能是资产，不一定是文献；进入 works 前必须有人审。
- agent 检索可能幻觉 URL；回填协议必须要求 URL 可验证或标低置信。
- 搜索方案生成可先用规则，LLM/agent 起草作为增强，不作为唯一来源。
